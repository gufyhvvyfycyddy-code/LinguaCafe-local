## 1. 口径与限制

两个仓库当前没有可解析的共同 Git 祖先，因此不能用“从共同提交以来新增了多少行”表示开发历史。本报告采用同一文件范围，对两个提交快照逐个统计。

生产与工具代码口径：

- 后端：`app/**/*.php`、`routes/*.php`、`config/*.php`
- 前端：`resources/js/**`、`resources/sass/**`
- 数据库：`database/**/*.php`
- Python：`tools/*.py`
- 单独统计：`tests/**` 与 Markdown 文档

不包含 `vendor`、`node_modules`、编译产物、数据库内容和未跟踪临时文件。

### 3.1 官方原项目的结构

官方原项目是典型 Laravel + Vue 单体应用：

- Controller 较薄，主要调用 20 个通用 Service；
- Service 按 Book、Chapter、Dictionary、Import、Review、Settings、TextBlock、Vocabulary 等大功能划分；
- 主要状态集中在 Vue/Vuex 和少数大型页面；
- 没有 WordSense、sense-only FSRS、ReviewLog 治理、Preset、Custom Study、AI Study Card 等当前领域；
- 自动测试只有约 214 行，几乎没有可靠回归护栏；
- 没有 ADR 或正式模块契约。

优点是规模小、容易找到入口。缺点是一个 Service 或页面通常承担完整功能链，隐藏耦合和回归风险高。

### 3.2 当前版本的结构

当前版本在原单体上形成了较多领域边界：

- WordSense、ReviewCard、ReviewLog、FSRS、Occurrence 的职责较清楚；
- ReviewCard lifecycle、查询、序列化、导出、Saved Search、Preset、Custom Study、AI Study Card 均有专门 owner；
- 高风险写入有事务、权限、拒绝路径和浏览器验收；
- Reader、Reviewer、Settings、Browser 等页面已进行多轮职责抽取；
- ADR、模块契约、测试和真实页面 evidence 已形成体系。

但当前仍是“分层后的大型单体”，不是完全按领域打包的模块化系统：

- `app/Services` 有 142 个文件，多数仍平铺在一个目录；
- 50 个 Service 不超过 100 行，18 个不超过 50 行，部分抽取可能只转移代码而没有降低认知成本；
- 路由数量接近翻倍，Controller 和 Service 导航成本上升；
- Reader、Reviewer、Dictionary Import 仍有多个 900–2,000 行热点；
- legacy word review 与 sense-only 主线并存；
- 文档、测试和状态 guard 中存在旧阶段与精确行数锁定。

## 4. 结构指标解释

### 4.1 集中式大文件

官方原项目主要热点：

- `TextBlockGroup.vue`：2,015 行
- `DictionaryImportService.php`：1,158 行
- `textThemes.js`：1,034 行
- `PatchNotes.vue`：1,032 行
- `VocabularyService.php`：803 行

当前主要热点：

- `TextBlockGroup.vue`：1,993 行
- `SenseReview.vue`：1,249 行
- `CustomStudySessionState.php`：1,176 行
- `DictionaryImportService.php`：1,158 行
- `TextBlockService.php`：1,077 行
- `Review.vue`：1,025 行

结论：旧 Reader 核心并未被彻底替换；当前版本增加了新的复杂领域，并通过多个 owner 降低部分耦合，但总体热点数量仍然较多。

### 4.2 前端请求所有权

官方原项目约有 117 个 `axios.` 引用，当前约有 221 个。考虑前端代码增长后，请求引用密度没有明显下降。这说明部分区域已经抽出 API client，但整个前端尚未形成统一 transport 层。

已经发现的点击词语重复请求正是这一结构的现实表现：不同显示组件仍可能各自拥有请求副作用。

### 4.3 后端依赖密度

虽然当前 `DB::`、`Auth::` 和手工 `new Service()` 的绝对数量增加，但后端体量增长更快，相对密度有所下降。说明依赖注入、专用查询服务和领域 owner 的方向总体有效。

## 5. 测试代码是否可以删除

### 5.1 当前测试组成

| 类型 | 文件数 | 行数 |
|---|---:|---:|
| Feature PHP | 151 | 70,949 |
| Unit PHP | 32 | 11,180 |
| JS/Node | 79 | 10,920 |
| 其他 | 2 | 79 |
| **合计** | **264** | **93,128** |

测试代码约为生产与工具代码的 91%。这个比例本身不能证明测试过多，因为当前版本新增了 FSRS、权限、导入、生命周期、删除、AI 边界等高风险功能；但测试维护成本已经成为独立问题。

启发式扫描发现约 87 个、16,262 行测试包含源码或文档 guard 特征，约占测试总量 17.5%。其中不代表全部可删除，只说明这是优先审计池。

### 5.2 现在不能删除的测试

以下测试在对应功能存在期间不得因为“原项目没有”而删除：

- FSRS 评分、间隔、撤销和 ReviewLog；
- ReviewCard identity、lifecycle、删除、归档、恢复；
- 用户和语言权限隔离；
- WordSense 与来源绑定；
- 导入事务、重复数据和失败恢复；
- Preset、Custom Study session token 和 eligibility；
- AI provider default-off、secret、外发和人工确认边界；
- 新账号初始化、数据库迁移和关键 schema；
- 真实复现过的回归 Bug。

这些测试是当前架构比原项目更可靠的主要原因。

### 5.3 可以进入删除或合并审计的测试

#### A. 精确文案、行数和阶段状态 guard

例如：

- 强制某个 Vue 文件必须正好 668 行；
- 强制文档必须包含某个日期标题；
- 强制已关闭阶段继续写 `not started`；
- 强制出现某个历史 Agent 名称。

这些不是长期业务不变量。应替换为职责、接口、危险调用缺失等语义检查；替换完成后删除旧断言。

#### B. 只扫描源码字符串的重复 UI guard

如果同一行为已经有：

- 组件级行为测试；
- 后端 contract test；
- 真实浏览器 smoke；

那么只检查按钮文案、方法名或源码片段的 guard 可以合并。不能先删 guard，再假设浏览器测试会覆盖。

#### C. 同一 endpoint 的重复排列测试

大型测试文件中可能重复创建相同 fixture，只改变一个无风险显示字段。可通过数据驱动、共享 fixture、参数化用例和 contract helper 压缩；优先“合并实现”，不是减少风险场景。

#### D. 已关闭迁移阶段的临时测试

只在一次迁移或临时脚本存在期间有效、且正式 schema/行为测试已经接管的测试，可以删除。必须先证明生产代码不再引用该临时路径。

#### E. legacy 测试

只能在对应 legacy 代码和公开入口经过产品决定正式移除后一起删除。当前 `target_type=word` 和 legacy Review 仍存在，因此不能先删测试。

### 5.4 推荐删除门槛

一个测试只有同时满足以下条件才可删除：

1. 它保护的行为已不存在，或被另一个更稳定测试完整覆盖；
2. 删除后仍有正常路径、拒绝路径和关键副作用证据；
3. 不涉及权限、数据丢失、FSRS、ReviewLog、导入、删除或外发；
4. 相关模块负责人和产品语义已经稳定；
5. 定向测试、全量受保护矩阵和真实页面验收通过；
6. 删除理由能写成具体不变量，而不是“测试太多”。

### 5.5 当前可压缩规模估计

不建议直接承诺删除比例。合理的第一轮只审计文档/源码字符串 guard 池：约 16,262 行。经过逐项映射后，预计其中只有一部分可以真正删除，其余应重写为更稳定的契约测试。

大型 Feature tests 更适合拆分和共享 fixture，不能以减少行数为目标批量删除。

## 6. 屎山程度评估

评分中的 10 表示职责混乱、隐藏副作用多、难以测试和难以安全修改。

| 维度 | 官方原项目 | 当前版本 | 说明 |
|---|---:|---:|---|
| 职责集中 | 7.5 | 6.0 | 当前已抽 owner，但 Reader/Reviewer/import 仍大 |
| 隐藏耦合与副作用 | 7.0 | 5.2 | 当前事务、Policy、Query Service 较清楚 |
| 可测试性风险 | 9.0 | 3.5 | 原项目几乎无测试；当前护栏较强 |
| 重复与兼容负担 | 4.5 | 7.0 | 当前有 legacy、双路径和多阶段兼容 |
| 导航与认知成本 | 4.5 | 7.0 | 当前 142 Services、30 ADR、近 9.3 万行测试 |
| 文档/治理漂移 | 3.5 | 7.5 | 当前存在历史正文、旧 guard、精确数字锁定 |

综合判断：

- **官方原项目生产代码屎山程度：约 6.7/10。** 规模小，但大组件、宽 Service、直接状态和几乎无测试使修改风险高。
- **当前版本生产代码屎山程度：约 5.7/10。** 核心领域设计更合理、写入更安全，但仍有大页面、兼容层和 transport 分散。
- **当前整个仓库维护负担：约 6.4/10。** 加入测试、文档和 guard 后，认知负担高于纯生产代码评分。

因此，问“谁的架构更合理”，答案是当前版本；问“谁更容易快速看懂”，答案是原项目；问“谁的代码耦合型屎山更重”，答案是原项目；问“谁的仓库治理和维护泥沙更多”，答案是当前版本。

当前版本不是把旧屎山完全拆掉，而是在原单体上建立了更可靠的领域结构，同时积累了大量保护层和历史层。下一阶段应减少重复、过期 guard 和兼容泥沙，不能通过删除核心测试回到原项目的脆弱状态。

## 7. 当前协作方式

当前有效方式：

1. 本地 Codex 直接处理；或
2. 网页端 GPT 通过 DevSpace 直接处理；
3. 两种方式都优先使用 FastCtx。

已停用：

- “一个主执行 Agent 对全部结果负责”；
- OpenCode / CodeBuddy / WorkBuddy 接力。

未来规划但尚未完整实现：网页端 GPT 制定计划，将互不冲突的工作分别交给网页端 DevSpace 和本地 Codex++；Codex++ 接入 DeepSeek Flash，并可进一步指挥接入相同 API 的扩展并行执行。

并行方案正式启用前必须解决：

- 单一任务账本与责任分配；
- 文件写入白名单和冲突检测；
- 同一文件禁止并行修改；
- 数据库写入和 Feature tests 串行；
- FastCtx 读写证据；
- 汇总方重新检查最终 diff；
- 任一分支失败时不得由另一方自动扩大范围补做。
