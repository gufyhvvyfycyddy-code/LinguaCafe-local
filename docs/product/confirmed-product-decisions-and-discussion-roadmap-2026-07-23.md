# LinguaCafe 已确认产品方向与后续讨论路线

> 状态：Current / Product Decisions
> 日期：2026-07-28
> 用途：只记录用户已经明确接受的产品方向，以及尚未冻结、必须继续讨论的议题。本文不代表任何代码实现已经授权。

## 1. 产品定位

LinguaCafe 不是通用 Anki 复制品。它继续以“阅读中识别词义、保留原文证据、形成 sense-only 复习卡”为核心，同时吸收 Anki 在备份、搜索、统计、Custom Study、Browser、导出、复习设置和插件接口方面的成熟能力。

## 2. 已确认、可进入规划的功能

### PD-001 自动备份与恢复

产品方向已接受。

最低完整体验：

1. 自动建立带时间的备份。
2. 用户可以查看备份列表、时间、范围和状态。
3. 恢复前说明会覆盖什么。
4. 恢复前再建立一个安全快照。
5. 恢复失败不能留下半恢复状态。
6. 先覆盖数据库、文章与文章结构；多媒体不进入当前范围。

### PD-002 WordSense 标签

产品方向已接受。

- 标签属于 WordSense 内容对象，不属于 ReviewCard。
- Card Marker 继续表示“这张卡需要关注”；WordSense Tag 表示“这个词义属于什么知识分类”。
- 支持一个词义多个标签、批量编辑、搜索、Saved Search、Custom Study 和统计。
- 是否支持层级标签、标签颜色和同义标签合并，留到实现 Spec 决定。

### PD-003 统一搜索条件

产品方向已接受。

同一套查询条件应逐步供以下功能复用：

- Browser；
- Saved Search；
- Custom Study；
- 统计范围；
- 导出；
- AI 批量整理。

不要求一次复制 Anki 全部搜索语法。先统一 LinguaCafe 已有条件的名称、含义和组合方式。

### PD-004 更完整的统计

产品方向已接受。

优先统计：

- 未来 7、30、90 天预计复习量；
- 真实保持率；
- Again / Hard / Good / Easy 使用分布；
- 稳定性、难度、可提取性分布；
- 容易忘记或持续失败的词义；
- 阅读量 → 生词 → 已确认词义 → 复习卡的转化；
- 文章来源对学习成果的贡献；
- 可按统一搜索条件改变统计范围。

所有指标必须先定义计算口径，避免不同页面出现同名不同数值。

### PD-005 `.apkg` 导出 V1

产品方向和首版卡面内容已接受。

导出单位：一个 WordSense 对应一张 Anki 卡。

卡片内容：

```text
单词：<surface 或 lemma，显示规则待卡面 Spec 决定>
释义：{{挖空 1}}

1. 原文：<该词义绑定的真实例句 1>
   翻译：{{挖空 1}}
2. 原文：<该词义绑定的真实例句 2>
   翻译：{{挖空 1}}
3. ……
```

冻结规则：

1. 例句使用这个 WordSense 对应的全部真实来源例句，并用有序列表排列。
2. 释义位置挖空。
3. 每条例句的中文翻译位置挖空。
4. 没有翻译时如何展示、例句过多时是否设上限、是否包含 FSRS 调度记录、重复导出如何更新，尚未冻结。
5. 当前只接受 `.apkg` 导出，不等于接受与 Anki 双向同步。
6. 当前不考虑图片、音频或其他多媒体。

### PD-006 文章健康检查

产品方向已接受，但当前范围只包括文章，不包括多媒体。

至少检查：

- 文章、章节和处理后正文是否完整；
- 章节顺序和段落结构是否异常；
- Tokenizer 是否降级；
- URL、邮箱、路径等不可学习片段是否污染词汇；
- WordSenseOccurrence 是否指向存在的文章和句子；
- 原文定位是否大量 fallback；
- 空文章、重复章节、孤立来源和损坏导入记录；
- 修复前预览和备份。

### PD-007 Custom Study 向 Anki 成熟能力靠拢

产品方向已接受：卡片在独立 Custom Study 入口中学习，兼容的能力尽量学习 Anki。

当前代码仍是 preview-only。以下语义必须在后续讨论中冻结后才能改 Harness：

- 临时学习是否正式评分；
- 正式评分是否影响正常队列；
- 提前复习、增加今日新卡、处理积压和搜索结果临时学习的差异；
- 会话结束后如何回归正常队列；
- 同一张卡当天重复进入多个临时会话时如何处理。

因此本条是“产品方向已接受，评分语义待讨论”，不是实现授权。

### PD-008 复习设置继续对齐 Anki

产品方向已接受。

- Anki 已有且与 sense-only FSRS 兼容的设置，可以逐步引入。
- 完全不兼容、依赖 sibling cards、任意 deck 树或通用 Note Type 的设置放弃。
- 每项设置必须说明用户影响、默认值、是否追溯旧卡、是否需要显式重排。
- 不允许为了“设置更多”而把内部参数全部暴露给普通用户。

### PD-009 Browser V2 与 AI 重复词义整理

产品方向已接受。

Browser 可继续增加：

- WordSense Tag 批量管理；
- 更丰富的列和排序；
- 统一查询条件；
- Saved Search 进入 Custom Study；
- 重复词义检测和整理。

重复词义的 AI 辅助流程采用离线文件闭环：

1. LinguaCafe 打包一个词义文件库，只包含整理所需的数据。
2. 页面提供固定提示词和复制入口。
3. 用户把提示词与文件交给外部 AI。
4. AI 返回固定格式结果。
5. LinguaCafe 只做解析、差异预览和人工确认。
6. AI 可以指出“完全重复”“近义但缺少区分”“可能应合并”“应保留为不同义项”。
7. AI 不得直接删除、合并或改写 WordSense；正式变更必须由用户确认，并有备份和撤销方案。

文件格式、提示词、置信度、批量确认和撤销细节留到独立 Spec。

### PD-010 受控插件接口

产品方向已接受。LinguaCafe 需要插件接口，但不等于允许插件任意修改内部数据库。

首要原则：

- 插件通过版本化接口工作；
- 明确声明权限；
- 默认最小权限；
- 调度、ReviewLog、用户权限、删除和密钥属于受保护能力；
- 插件失败不得拖垮阅读和复习主流程；
- 插件兼容版本、启停状态和错误必须可查看；
- 优先支持导入器、词典、AI Provider、导出器和只读分析插件。

插件的安装来源、签名、审核、沙箱、移动端支持和收费模式尚未冻结。

### PD-011 已接受的架构优化

以下方向已接受：

1. 建立稳定的请求/响应契约，不再让多个页面自己猜 payload。
2. Service 按领域归档，不按行数机械合并或拆分。
3. Search、Custom Study、统计、导出共用查询模型。
4. Tokenizer、Jellyfin、Anki、WebSocket 等使用统一 Capability / Readiness 状态。
5. 各类撤销操作建立统一目录和用户说明。
6. Harness 保护用户行为、数据和权限，不再锁定文件精确行数、旧日期或旧阶段文案。

### PD-012 阅读中直接刷词义卡 V1

> 产品语义冻结日期：2026-07-24。
> 状态：已冻结，可进入架构 Spec 与分阶段实现；尚未授权修改业务代码。

#### 评分何时生效

1. 用户点击绿色词后，先选择 Again / Hard / Good / Easy。
2. 这一步只形成浏览器内的“待确认评分”，不写数据库，不创建 ReviewLog，不改变 FSRS，也不增加复习次数。
3. 用户随后确认当前句子对应的具体 WordSense；只有确认成功后，待确认评分才正式落到该 WordSense 的 ReviewCard 上。
4. 一个句子中的一个目标词只能选择一个主要词义，不允许多选。
5. 用户取消整个流程时，待确认评分立即清空，不留下任何正式或临时学习记录。

#### 已有词义与新词义

1. 已有多个词义时，一次列出全部候选，但只能选择一个“是这个意思”；列表下方提供统一的“都不是”。
2. 选择“都不是”后回到正常查词界面，并保留本次待确认评分，以便用户继续添加真正符合当前句子的词义卡。
3. 用户成功创建新 WordSense 和 ReviewCard 后，待确认评分可以落到这张新卡上。
4. 用户在添加新词义界面点击取消、关闭当前查词流程或切换到另一个词时，待确认评分清空。
5. “都不是”本身不创建词义、不写 ReviewLog、不改变 FSRS。

#### 重复点击与 Again 后续步骤

1. 用户可以再次点击同一个单词并完整走一遍界面，但同一张 ReviewCard 不得因为重复操作而被重复计为正式复习。
2. 如果两次最终确认的是不同 WordSense，例如第一次 `run=跑`、第二次 `run=运行`，两次评分分别落到两张不同的词义卡上，可以各自生效一次。
3. 阅读页只负责当前这一次正式评分，不实现 10 分钟计时器，也不在文章内完成 Again 后的第二次学习/重学步骤。
4. Again 或其他进入短学习步骤的评分，后续步骤由正式复习队列接管；是否已经到期、何时出现，沿用正式复习队列和 FSRS 的规则。
5. 重复抑制必须按 ReviewCard 判断，不能只按单词拼写判断。

#### Ctrl+Z

1. 在正式写入之前，Ctrl+Z 撤回界面步骤：可重新选择评分或词义，不调用后端撤销。
2. 在词义确认并正式写入之后，Ctrl+Z 必须复用正式复习现有的 ReviewLog 快照撤销，恢复卡片原状态。
3. 正式撤销成功后，界面回到词义选择阶段，并恢复刚才的待确认评分，使用户可以重新选择正确词义。
4. 文本输入框获得焦点时，不拦截浏览器原生 Ctrl+Z。

#### 译文显示

1. 是否查看译文由用户决定，不能由系统强制规定。
2. “显示译文”按钮始终可见。
3. 第一次点击进入“隐藏着显示”模式：译文区域存在，但只有鼠标悬停或键盘聚焦时显示；移开后再次隐藏。
4. 第二次点击进入持续显示模式，译文保持可见。
5. 为形成完整状态机，当前实现候选采用第三次点击回到关闭状态；这一循环细节需要在真实页面验收时确认是否自然。
6. 本条只冻结译文的显示控制，不冻结“一句一行”或“连续正文预留空间”等整体排版方案。

#### 实现边界

- 新流程不得把当前 `/senses/inline-confirmation` 直接改造成评分接口。
- 正式评分必须继续通过统一的 Sense Review 写入路径、ReviewLog、FSRS 调度和撤销机制。
- 当前阅读确认历史可以保留，但它与正式评分是两个不同概念。
- 实现时必须同步更新 ADR、Spec、Harness，并进行真实 MCP Chrome 验收。

### PD-013 云端主导移动化与有限离线

> 产品规划基线日期：2026-07-28。
> 状态：路线基线已存档，并已由后续 M1–M18 实现链消费；不代表 Android/iOS、离线同步、iOS 发布能力或商业化已经完成，也不构成当前下一任务授权。

1. Laravel 服务端和中央数据库继续作为账号、WordSense、ReviewCard、ReviewLog、FSRS、文章与 AI 数据的权威来源。
2. 网页端继续承担文章导入、Browser、设置、统计、备份、批量治理和高级管理。
3. Android/iOS 主要承担阅读、查词、简单词义创建、日常复习、提醒和进度查看。
4. 移动端采用有限离线：下载文章包与短期复习包，离线操作进入本地队列，恢复网络后幂等上传。
5. 不建设 Anki 式每台设备完整权威数据库、任意时长完整离线和完整 collection 合并协议。
6. 继续保留与 LinguaCafe 相容的 Anki 能力，包括 FSRS、四档评分、ReviewLog、Card Info、Browser、标签、统计、Custom Study、撤回、备份和 `.apkg` 导出；必要时改变后台实现，不因云端路线删除用户功能。
7. 2026-07-28 当时唯一推荐的下一技术里程碑是 Mobile API Foundation 与正式评分幂等；该历史决定已被后续 M1–M18 实现链消费。当前不得再把 M1 写成下一任务，剩余能力必须按最新 milestone lock 与独立授权判断。
8. 可继续吸收的 Anki 能力已拆为 M10–M18：统一查询/标签/Browser、手动调度、专项学习、复习设置与负担模拟、完整统计、Browser 数据治理、便携数据、自动推进/无障碍和媒体完整性；它们必须按依赖穿插，不要求全部挡在移动端之前。
9. 详细成本、边界与里程碑见 `docs/plans/cloud-first-mobile-product-and-technical-milestones-2026-07-28.md`。

## 4. 已提出但尚未冻结的议题

### DISC-001 无密码档案选择

用户希望参考 Anki 桌面端：启动后直接选择档案，不要求输入密码。

已核查的 Anki 事实：

- 桌面端可以建立多个 Profile，每个 Profile 有独立 collection 和设置。
- Profile 窗口支持打开、新增、重命名、删除和恢复备份。
- AnkiDroid 不支持桌面式多 Profile。
- 一个需要同步的 Profile 要使用独立 AnkiWeb 账号；多个 Profile 不能共用同一同步账号。

因此尚未冻结：

- LinguaCafe 是完全本地单人软件，还是仍允许远程访问；
- 无密码模式是否只允许本机；
- 手机端如何安全选择档案；
- 付费同步、云端数据和管理员操作是否仍需要认证；
- 丢失或被他人使用设备时如何保护数据。

在这些问题解决前，不删除现有密码和权限代码。

### DISC-002 阅读中直接刷卡（已关闭）

本讨论编号已于 2026-07-24 完成冻结，正式决定已迁移到 `PD-012 阅读中直接刷词义卡 V1`。当前代码仍是旧的阅读确认流程；“讨论已关闭”不代表实现已经完成。

### DISC-003 新文章的 AI 生词建议流程

用户提出：系统先标出生词并打包给 AI，用户粘贴 AI 返回文本，再进入一个默认开启、可在设置关闭的批准步骤；第一次出现时，在确认窗口中用一行文字说明关闭路径。

尚未冻结：

- “系统标出生词”使用何种标准；
- AI 推荐默认是否勾选；
- 批准的是单词、词义还是生成卡片；
- 首次提示是一次性、每个档案一次，还是每种语言一次；
- 该流程和现有 AI Study Card V1–V5 如何合并，避免第二套重复流程。

### DISC-004 翻译显示与文章排版

用户确认当前“显示翻译后页面伸缩、关闭后位置跳动”的体验不可接受。

候选方向：

1. 一句话一行；每段显示段落编号，段末增加分隔线。
2. 保持连续正文，但预留翻译高度，并让英文句子位于翻译上方。

尚未冻结：默认方向、长句处理、窄屏表现、翻译缺失时的留白、段落编号样式和是否允许用户切换布局。

## 5. 后续讨论安排

至少分四轮，不把多个高风险决定塞进同一轮。

### 第 1 轮：阅读中直接刷卡（已完成）

2026-07-24 已冻结：待确认评分、单一 WordSense 选择、“都不是”进入正常查词并可把评分落到新建卡、取消即清空、同卡重复抑制、Again 后续由正式复习队列接管、两阶段 Ctrl+Z，以及译文关闭/悬停显示/持续显示三态。下一步只能先做架构 Spec、ADR 和 Harness 迁移设计，不能直接把旧 inline confirmation 接口改成评分接口。

### 第 2 轮：AI 阅读入口与翻译排版

讨论新文章生词识别、AI 文件闭环、批准步骤、首次提示，以及一句一行和连续正文两种翻译布局。目标是形成 Reader 产品 Spec，不讨论商业收费。

### 第 3 轮：档案、手机端和同步身份

讨论无密码本地档案、远程访问、移动端身份、跨设备同步和数据安全。先决定“谁可以打开哪个档案”，再讨论技术平台。

### 第 4 轮：三平台、插件和商业模式

## 6. 文档与 Harness 处理规则
