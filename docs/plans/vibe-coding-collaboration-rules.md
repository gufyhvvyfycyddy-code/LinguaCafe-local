# LinguaCafe AI 协作与交付规则

> 当前权威版本：2026-08-06。
> 根级硬规则见 `AGENTS.md`；本文件解释任务如何落位、执行和验收。业务状态见 `docs/DOCUMENTATION_INDEX.md`。Git 历史保留旧版长文，不在当前上下文继续携带已停用工作流。

## 0. 权威、目标与阅读方式

1. 本文件不得覆盖 `AGENTS.md`、已接受 ADR 或用户当前明确决定。
2. 新任务先从文档索引进入，只读当前模块需要的章节；不把本文件、master plan、全部 ADR 和字幕一次性塞进上下文。
3. 本文件只保留长期协作流程。GLM/OpenCode/CodeBuddy/WorkBuddy 等具体工具或旧角色不是架构事实，不作为当前硬规则。
4. 规则的目标是降低未来决策次数和越界概率，不是让提示词更长、任务更复杂或模型工作更久。

## 1. 决策责任

- 用户决定产品目标、优先级、风险授权和是否接受长期规则。
- 执行 Agent 负责读取真实代码、提出最小方案、实施、运行外部验证并报告事实。
- AI 可以起草 spec、ADR、测试和架构候选，但不得把自己的建议自动升格为产品决定或长期规则。明确持续目标中，用户按 ADR-0034 委托的 Anki 映射或最小可逆实现选择可直接记录和验证；这不等于授权 Agent 改变产品边界、安全模型或不可逆语义。
- 报告、测试绿灯和 Agent 自审都不能代替用户的产品判断。

### 1.5 当前执行方式

当前有效方式只有两种：

1. 本地 Codex 直接处理；
2. 网页端 GPT 通过 DevSpace 直接处理。

两种方式在文件发现、搜索、读取、替换和命令执行中都优先使用 FastCtx。旧“一个主执行 Agent”规则以及 OpenCode / CodeBuddy / WorkBuddy / GLM 接力流程均已停用，不得重新写成当前要求。

Reasonix 作为并行核查者运行时，主执行方不得停工等待。主执行方必须继续做可以独立推进的侦察、测试、验收或实现，并周期性检查 Reasonix 的阶段结果，把已完成结论及时吸收到当前判断。只有下一步客观上只能依赖 Reasonix 返回时，才允许短暂等待。

当前允许多个网页端 GPT / 本地执行窗口并行，但只能使用有边界的并行闭环：

1. 每个并行窗口必须有唯一任务 owner，且写入文件集合互斥；只读检查可以重叠，写入责任不能重叠。
2. 共享 testing DB 的 PHPUnit 必须串行执行并持有同一测试锁；不得用并行 Feature 测试争用共享状态。
3. Node guard、前端构建和纯文档工作只有在不争用文件、输出目录或构建资源时才可并行。
4. 长任务必须使用 FastCtx 持久后台 job；任务断线后通过原 job ID 恢复和读取结果，不得重复启动同一工作。
5. 最终只由一个主窗口统一复核、精确暂存、commit 和 push；并行窗口不得各自在同一 working tree 上提交。
6. 发现其他窗口正在修改同一文件时，当前窗口立即停止该文件的写入，保留现有改动并重新分配 owner，不得覆盖、回退或抢占。

历史兼容说明：旧规则曾把“网页端 GPT 与本地 Codex++ 并行”写成“未来方向、尚未完整实现”。该旧判断已失效，只保留这句话用于说明 guard 的历史迁移背景，不得据此否定本节已经生效的有边界并行闭环。

## 2. 任务进入条件

每个任务在实施前冻结一个小切片：

1. 目标与不做事项。
2. 当前事实和根因证据。
3. 模块责任、接口/seam、数据流。
4. 允许文件与禁止文件。
5. 受保护行为和数据写入边界。
6. 最小可执行验收与停止条件。

纯文档、纯验证、单文件修复可以独立成任务。不得为了“复合任务”、复杂度分数或进度百分比强塞架构改造、功能开发、DTO、Service 或额外测试。

## 3. 上下文与文档分层

### 3.1 五层上下文

1. `AGENTS.md`：每次加载的稳定硬规则。
2. `docs/DOCUMENTATION_INDEX.md`：只负责路由当前权威文档。
3. ADR / 模块契约：按受影响模块加载。
4. 源码、接口和相关测试：按任务加载。
5. 错误输出、临时计划和对话历史：仅本轮使用。

历史状态、已关闭报告、一次性调试记录不得混入当前指令。文档不一致先按范围、阶段、supersession 和 `AGENTS.md` 权威层级处理；低权威旧状态只在当前 allowlist 内更新，范围外登记即可。只有同一最高有效权威仍存在实质冲突时停止，不让模型猜。

### 3.2 文档职责

| 信息 | 唯一落点 |
|---|---|
| 长期安全、范围、停止规则 | `AGENTS.md` |
| 当前入口和文档路由 | `docs/DOCUMENTATION_INDEX.md` |
| 当前工作台 | `docs/plans/current-working-handoff.md` |
| 长期工作登记 | `docs/plans/linguacafe-master-plan.md` |
| 稳定技术决定及理由 | `docs/adr/` |
| 模块责任、接口与数据流 | `docs/architecture/` 或模块 contract |
| 可执行不变量 | tests / smoke / harness |
| 旧状态和执行报告 | `docs/history/` |

同一规则只能有一个权威正文；其他文档只链接，不复制。未来计划不得写成已实现，临时修复不得写成永久原则。

## 4. Spec 生命周期与 Harness

### 4.1 规则晋升门槛

候选决定必须由用户明确冻结；除核心产品章程/排除项外，还要经过真实实现/验收，再选择落点。只有稳定、重复相关、违反代价高且可验证的决定才进入 spec、ADR 或硬规则。

每次纠正 AI 时问：“这会再次发生吗？”

- 否：只修当前问题。
- 会，但决定仍在变化：放 task plan。
- 会，决定已稳定：写 ADR / 模块 contract。
- 会，且破坏后难发现或代价高：同时加最小 test / smoke / harness。

### 4.2 Harness 最低标准

Harness 必须能独立完成：准备条件、执行真实路径、输出明确通过/失败。优先保护：

- 已稳定的核心用户流程。
- 权限、数据保存/删除、导入导出、ReviewLog/FSRS 等高风险写入。
- 重复出现的回归。
- 一旦出错很难定位的跨模块链路。

不追求覆盖率数字，不为每条自然语言 spec 配测试。一个公开入口上的承重检查优于多个调用方的重复 guard。

## 5. Architecture Gate

风险等级与审批语义以 `docs/adr/ADR-0001-architecture-gate-workflow.md` 为准。

- 低风险：单文件、纯样式、纯文档、明确根因的小修。限制范围并做相称验证。
- 中风险：不改变既有语义的 props/events、前端 API 调用、工具函数或多文件同模块变更。按 ADR-0001 做最小上下文、必要的接口设计和实施后质量审查。
- 高风险：Vuex/store 逻辑、后端 endpoint、请求/响应 payload 或公开接口语义、跨模块、数据模型、核心写入、FSRS、WordSense、ReviewCard、AI、reader 状态流、import/export。先做任务范围架构审查；普通任务由用户确认后实施，明确持续目标按 ADR-0031/ADR-0034/ADR-0037 继承已冻结 roadmap 的执行授权、自主决策梯与非阻断执行前沿。

架构审查必须回答：谁拥有责任、接口是什么、复杂度藏在哪里、会跨哪些 seam、允许/禁止文件、兼容风险、验证方式、是否需要 ADR。

高内聚低耦合不等于拆得越碎越好。删除一个模块若只会把同样复杂度搬到调用方，该模块没有带来 depth；只有真实的第二个调用者或适配器出现时，才考虑新增抽象 seam。

### 5.1 目标模式 roadmap 执行授权

用户明确创建或恢复一个指向权威 roadmap 或有序里程碑的持续目标时，目标授权依赖顺序内的全部切片。架构审查必须在目标点名范围内冻结当前切片的具体范围，并用计划、ADR、契约和测试约束其数据、接口和兼容语义；只忠实展开已接受 roadmap 的切片文档按 ADR-0037 视为 `Accepted under current goal authorization`，不再形成逐份人工闸门。执行 Agent 完成相称验证和逐项完成审计后可自动进入下一命名里程碑；当前里程碑锁若明确写有 `auto_advance: false`、`supervisor_unlock_required: true` 或等价停止条件，则该局部锁优先，必须停止等待验收或新授权。

目标授权可覆盖冻结里程碑明确需要的 additive migration 文件、testing 专用数据库 schema、新表、新 Controller/Service/model/middleware/store module、已审查的多个 seam 和已冻结的高风险领域语义。计划未写死的可逆选择按 ADR-0034 的“当前用户决定 → 已接受 ADR/契约/roadmap → 经核实稳定先例 → Anki 官方行为及 LinguaCafe 映射 → 最小可逆推荐”处理。保留停止条件为：开发/预发布/生产或真实用户数据上的 migration、回填、恢复、删除和破坏性操作；真实 AI provider、密钥、外发、付费、模型或成本上限；部署、签名、商店提交等不可逆第三方动作；未被委托的实质产品边界变化、同一最高有效权威冲突或目标外扩张。保留停止线只暂停受影响依赖分支；仍有独立切片时继续执行。完整语义以 ADR-0031、ADR-0034、ADR-0037 和 `AGENTS.md` 为准。

## 6. 实施纪律

1. 先读将修改的完整文件、全部调用方、相关接口和测试。
2. 优先修共享根因，避免在每个调用方打补丁。
3. 复用 upstream、现有 helper、框架能力和已安装依赖。
4. 不顺手清理，不提前搭“以后可能用”的脚手架。
5. 不并行修改同一文件，不并行运行争用同一 testing 数据库的写测试。
6. 每个小切片保持可运行；同一冻结责任内的新文件/seam 先更新 Architecture Gate 和 allowlist 后继续。脏工作区先读 diff 后语义合并，不因文件已修改而停工。超出切片、未被 ADR-0034 委托的实质产品决定或保留停止线只暂停受影响分支。
7. 架构变化与功能变化能分开验证时分开提交；纯机械整理不得掩盖行为变化。

## 7. 验收闭环

验收按风险选择，不机械执行全仓测试：

1. 静态范围检查：最终 diff、允许文件、禁止模式、秘密和生成物。
2. 聚焦自动测试：覆盖修改接口、正常路径、拒绝路径和关键副作用。
3. 受保护模块回归：按 `AGENTS.md` 验证矩阵触发。
4. 前端构建：前端或前后端契约变化时运行。
5. 真实页面验收：可见 UI、reader、review、import/export 变化时运行，并检查 Console / Network。

真实页面验收不绑定某一个浏览器工具。优先使用官方 OpenAI Browser/Chrome 插件；普通失败后按 `docs/plans/mcp-chrome-local-smoke-playbook.md` 的降级顺序切换 Chrome DevTools/MCP、受控 Playwright、Computer Use/系统浏览器或其他项目批准通道。只要实际页面被渲染并通过 DOM/用户事件操作，即属于真实页面验收。

API、源码阅读、截图或 Agent 自述不能代替真实页面操作。所有平台允许通道均失败，或存在验证码、双重验证、系统级授权等必须由人处理的步骤时，持续目标先记录 `Acceptance Deferred — Not Complete` 并继续独立切片；只有没有其他可运行切片或最终完成审计需要该动作时才请求用户。不得因单一工具拒绝 localhost 就提前停工。

若 system、developer 或工具输出明确禁止同一结果的 workaround、间接执行、原始命令或 alternate surface，该安全拒绝不是普通通道失败，必须停止同一动作的降级尝试。

### 7.1 固定本地验收身份

LinguaCafe 本地浏览器验收统一使用“当前任务提示词提供的固定本地验收身份”。仓库文档、日志、截图和报告不得写入其明文账号或密码。

- 不修改或删除该固定身份，不创建随机邮箱、替代账号或批量本地用户来绕过登录问题。
- 登录失败时停止写入验收，诊断同一个固定身份的认证、数据库归属和权限状态；不得因自动化方便制造新的本地用户。
- 修复同一个固定身份的数据属于独立授权的数据操作，只有用户明确授权后才能执行；不得自动修改账号、密码或权限。
- 固定身份未能登录时，不得以 API、直接数据库写入或另建账号冒充真实页面验收通过。

验收证据仅因平台允许范围外的工具/环境原因缺失时，可使用 `Acceptance Deferred — Not Complete`。按 ADR-0052，Architecture Gate 证明下游只依赖已执行验证的契约、不触及缺失行为且没有已知产品缺陷时，可继续可逆、独立可测试的下游实现；缺失检查按 Android 设备、iOS 签名设备、商店提交等能力簇累计，不再用单个 deferred 的机械路径预算冻结实现。该里程碑和最终目标仍未完成，最终审计必须逐项清零能力簇。

## 8. 安全红线

`AGENTS.md` 是安全红线的唯一权威正文，本文件不复制清库、凭据、权限、写入、Git、任务外文件或完成 hook 规则。任务提示词只能收紧这些边界，不能放宽。

### 8.7 Anki 参考优先（兼容锚点）

涉及 Anki 评分、队列、自定义学习、卡面、字段、快捷键、撤销、学习步骤或复习顺序时，决策顺序固定为：Anki 官方手册/源码 → 保留核心语义的 LinguaCafe Web 适配 → Anki 没有对应设计时再做独立产品判断。不得用普通网页习惯覆盖 Anki 已有语义；Anki 未冻结视觉样式时，ADR 或计划必须明确标注“LinguaCafe 项目适配”。论坛和第三方模板不能冒充官方默认。

## 9. 报告与 Git

最终报告必须能由 Git 和命令输出复验：

- 实际改动文件及原因。
- 是否越界、是否触及数据或接口。
- 实际运行的命令、退出结果和未验证项。
- 浏览器结果或 `Incomplete`。
- branch、commit、push 状态。

只暂存精确文件。报告禁止写“应该通过”“大概完成”或虚构进度百分比。

## 19. 任务规模规则（取代复杂度分数）

任务规模由风险和可验证 seam 决定，不设最低复杂度、运行时长或百分比。

- 一个任务只交付一个可陈述结果。
- 文件数或 seam 明显增长时拆分。
- 小修不与无关架构工作捆绑。
- 高风险工作宁可缩小垂直切片，也不降低验证。

## 27. 模块边界与专项验证

### 27.0 第一原则（兼容锚点）

代码安全和稳定性优先于功能速度；具体安全、模块和写入不变量只以 `AGENTS.md` 为权威。

### 27.1 长期模块不变量

稳定模块责任、正式评分入口和 AI/只读边界只以 `AGENTS.md` §6 为权威。模块契约和 ADR 解释实现细节；本文件不复制类名、payload 或禁令。

### 27.5 页面与词元 smoke

涉及真实 token 点击时，按 `docs/plans/mcp-chrome-local-smoke-playbook.md` 和 `docs/plans/morphology-test-sample-tracker.md` 选新样本并真实点击。API/fetch/axios 不能冒充页面操作。某一个工具不可用时自动切换下一真实浏览器通道；只有全部可用通道失败后才标记 `Incomplete`。

### 27.7 Testing DB 健康检查

涉及 Feature tests 或数据库写测试时，先运行：

```bash
php artisan test --filter=TestingDatabaseHealthTest
php artisan test --filter=TestingDatabaseHealthConfigTest
```

失败时按 `docs/plans/testing-db-health-playbook.md` 处理；数据库安全边界见 `AGENTS.md` §9。

### 27.8 PHP 测试输出

高输出命令写入已忽略的临时日志，只返回退出码和末尾摘要。Unit 可独立运行；Feature 按文件或业务模块分组。失败处理的硬规则见 `AGENTS.md` §8。

## 28. 需求放置与报告闭环

### 28.1 单一权威来源

本节是需求落位与报告闭环的唯一正文；其他文档只链接和记录本轮结果。

### 28.2 需求处理

新需求先分类为：当前阻塞、当前兼容、未来阶段、独立主线或暂不进入计划。只有当前阻塞或天然兼容的需求可进入当前切片；其余登记到正确 plan/roadmap，不自动抢占下一任务。

落位必须说明阶段、理由、前置条件和为什么不提前做。明确 roadmap 目标内的位置先按依赖图、现有 registry 和 ADR-0034 决策梯自动确定；同一最高有效权威给出互不相容的优先级或需求位于目标外时，只暂停受影响分支，仍有独立切片则按 ADR-0037 继续。

### 28.3 架构检查与开发的关系

所有代码任务都要做与风险相称的架构检查，但不强制每个任务同时产生架构改造和功能代码。没有真实结构问题时，记录“无需结构改动”即可；禁止为了流程形式制造抽象、拆分或文档。

### 28.4 字幕使用

字幕是经验来源，不是项目权威。只按任务读取相关字幕；不得让字幕覆盖代码事实、ADR 或用户最新决定。采用字幕建议前，必须将其转为本项目可验证的触发条件；探索性意见不进入 spec。

本轮长期规则整合参考了用户提供的 9 份字幕，采用的稳定原则为：规则按需加载、spec 滞后于稳定决定、反向边界优先、关键不变量进入 harness、AI 延续而不创造架构、模块化需平衡接口成本、验收发生在 AI 输出之外。

### 28.5 报告处理

验收依次核查：用户要求 → 最终 diff → 允许范围 → 测试/构建/浏览器证据 → 当前计划和未决产品选择。Accept、Refuse、阶段性 Accept 或 Incomplete 必须基于证据，不只依据 Agent 报告。

### 28.6 下一任务

普通任务完成后停止；不得把建议、future work 或报告中的 follow-up 自动实施。明确持续目标按 ADR-0031/ADR-0034/ADR-0037/ADR-0052 依有序里程碑继续；deferred 检查按能力簇追踪，保留停止线只暂停受影响动作。仅当没有任何可运行切片或最终审计需要人工清零时等待用户决定；最终完成审计必须清零全部 deferred 能力簇及命名检查。

## 29. 规则收敛检查

修改长期规则时最多进行三轮独立对抗审查。每轮按以下顺序分类：权威冲突、行为/安全漏洞、范围膨胀、无法验证、纯措辞。前四类必须修正；只剩纯措辞或同义建议时停止。规则越改越长本身不是进步，能删除重复且不丢失约束才算收敛。
