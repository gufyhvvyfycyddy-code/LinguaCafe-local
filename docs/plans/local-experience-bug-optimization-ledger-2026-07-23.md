## 一、账号治理记录

### [治理] U-001 本地主账号与内部自增编号说明

- 主账号：`当前任务提示词提供的本地测试账号`
- 当前数据库内部用户编号：`本地主账号内部自增 id`
- 当前权限：管理员
- 密码验证：通过
- 当前用户总数：1
- 主账号关联数据：1 本书、8 条词义、5 张复习卡

#### 内部自增编号的准确含义

`users.id` 是数据库自增主键。此前开发和测试过程中创建、删除过多批账号，自增编号会继续向后增长，因此当前主账号编号不必为 1。这个编号只用于数据库内部关联，不影响邮箱登录、管理员权限或用户看到的账号名称。

不应为了让编号变成 1 而强行重排。书籍、章节、词义、复习卡、设置、目标等数据都通过当前主账号内部 id 关联，直接改号会产生大量关联风险。

### [治理] U-002 测试账号清理结果

已删除 9 个历史测试身份及其残留目标、设置和复习预设。具体邮箱只保留在本地任务上下文，不写入公开仓库文档。

清理前核查显示，这些账号没有书籍、章节、词义、复习卡或待 AI 解释数据，只残留默认目标、设置、目标记录和测试预设。清理时先删除关联记录，再删除用户，避免遗留孤立数据。

### [治理][待优化] U-003 开发阶段账号上限规则

#### 规则

1. `当前任务提示词提供的本地测试账号` 是永久保留的本地主账号。
2. 主账号必须始终保有管理员权限。
3. 开发数据库中的用户总数不得超过 10。
4. 临时测试账号在对应测试完成后应删除。
5. 自动化测试优先使用测试数据库，不应持续向本地日常数据库写入新用户。
6. 删除测试账号时必须同步删除其用户级数据，不能只删 `users` 表记录。

#### 产生多余账号的原因

项目已有创建用户入口和大量真实浏览器验收，但没有完整的“删除整个用户”后台接口。管理员页面只能创建和编辑账号，现有删除功能只删除当前用户某一种语言的数据。测试账号因此会在本地数据库中持续累积。

#### 后续方案

增加管理员可用的“删除测试用户”功能，包含：

- 禁止删除当前登录账号；
- 禁止删除指定主账号；
- 禁止删除最后一个管理员；
- 删除前显示该账号关联数据数量；
- 使用事务清理全部用户级数据；
- 开发环境用户达到 10 个时给出警告。

## 二、Jellyfin 说明

### [体验] E-001 Jellyfin 是什么

Jellyfin 是一个可自行部署的影视媒体库服务。它可以管理本地电影、电视剧、音频和字幕，功能类似个人版流媒体平台。

LinguaCafe 中的 Jellyfin 功能只用于一种可选导入方式：从 Jellyfin 媒体库读取字幕，把字幕导入为阅读材料。普通文章、纯文本、电子书、本地字幕和词典使用都不依赖 Jellyfin。

当前前端在打开“导入阅读材料”窗口时，会请求全局设置 `jellyfinEnabled`，用来决定是否显示“Jellyfin 字幕”入口。当前项目没有这条全局设置，后端因此返回 500。对于未配置 Jellyfin 的本地用户，正确默认行为应为 `false`，直接隐藏该入口。

## 四、Bug 台账

### [Bug][后端问题][P0] B-001 Python tokenizer 服务未运行

#### 现象

导入英文文章时页面提示使用基础英文分词。后端连续记录：

- Python tokenizer 不可用；
- 使用 English fallback；
- 无法提供正常高级词形分析。

#### 精确原因

项目规定的 tokenizer 地址为 `http://127.0.0.1:8678`。执行 `scripts\windows\tokenizer-doctor.bat` 后，健康检查 `/models/list` 无法连接，说明当前没有可访问的 tokenizer 进程监听 8678。

项目启动脚本 `scripts/windows/tokenizer-start.bat` 会依次检查：

1. `tools/tokenizer.py` 是否存在；
2. Python 是否可用；
3. Bottle、spaCy、lxml、ebooklib、pykakasi、pinyin 等依赖是否齐全；
4. 然后才在新窗口启动 tokenizer。

本轮已经确认脚本文件存在，当前直接原因是服务没有启动。依赖是否完整需要在正式修复阶段继续执行启动脚本并读取启动窗口的具体结果，不能仅凭“服务不可达”推断依赖必然缺失。

#### 用户影响

- 规则变化词可能无法稳定归并到词元；
- 同一个词的不同形式可能成为多个学习对象；
- 哲学文本中的长词、派生词和过去分词更容易被拆散；
- 例句边界和段落边界质量下降；
- 后续词义卡、熟练度和复习统计可能分散。

#### 解决方向

1. 让本地统一启动流程自动启动 tokenizer，而不是依赖用户手工另开窗口。
2. 启动后调用 `/models/list` 和英文词形健康检查。
3. 导入前检测服务状态；不可用时显示强警告，并允许用户选择取消导入。
4. 验收至少覆盖 `technologies→technology`、`inherited→inherit`、`shaped→shape`、`organizes→organize` 等真实哲学文本词形。

#### 验收标准

- 8678 健康检查返回 2xx；
- 重新导入测试文章时不出现 fallback 提示；
- 后端不再记录 tokenizer unavailable；
- 阅读页词元归并正确；
- 不使用旧文章数据冒充修复成功。

### [Bug][后端问题][P1] B-002 首次登录统计初始化竞态

#### 现象

新账号首次进入首页时，`POST /statistics/get` 偶发 500：

`Attempt to read property "id" on null`

稍后刷新后请求恢复为 200。

#### 精确原因

`StatisticsService::getStatistics()` 先查询 `read_words` 目标，然后直接读取 `$readingGoal->id`。当目标尚未创建时，查询返回 `null`，随后解引用 `id` 触发异常。

账号创建和旧账号补目标依赖另一条初始化流程。前端进入首页时，目标读取/创建请求与统计请求并发发出，统计请求可能先完成，因此形成首次登录竞态。问题不在统计计算本身，而在后端假设“目标一定已存在”，且没有在同一个事务或同一服务入口中保证该前置条件。

#### 解决方向

- 创建用户时在同一个事务内创建所有默认目标；
- `StatisticsService` 仍需对缺失目标进行幂等补建或返回零值；
- 前端请求顺序不能作为数据完整性的唯一保障。

#### 验收标准

新建账号后第一次进入首页，统计请求必须直接返回 200；连续并发请求也不能出现空目标异常。

### [Bug][体验][P1] B-003 生僻词悬浮卡为空白

#### 现象

悬停 `technicity` 时会出现悬浮卡容器，但容器内部完全空白。点击该词后，右侧栏可以正常显示“暂无词典结果”。

#### 精确原因

`VocabularyHoverBox.vue` 只实现了以下显示分支：

- 用户自定义释义存在；
- 本地词典正在加载；
- 本地词典结果非空；
- API 词典结果非空或正在加载。

当所有来源都返回空数组时，没有任何 empty-state 分支。悬浮卡本身仍根据 hover active 状态渲染，因此用户看到一个空盒子。

#### 解决方向

增加明确空状态：

`本地词典暂未收录此词，点击可查看上下文或手动添加释义。`

空状态应区分“没有结果”“搜索失败”“词典被关闭”。

### [Bug][体验][P1] B-004 手动添加词义默认选择动词

#### 现象

为名词 `technicity` 添加词义时，表单默认词性为“动词 verb”。

#### 精确原因

`ManualSenseForm.vue::buildLocalForm()` 在没有预填词性时固定返回 `pos: 'verb'`。`WordSensesList.vue::emptyForm()` 也固定使用 `pos: 'verb'`。因此所有没有候选词性的新词都会被默认为动词，与当前词本身无关。

#### 解决方向

优先级建议：

1. 有词典词性时采用词典候选；
2. 有 tokenizer 词性时采用 tokenizer 结果；
3. 两者都没有时默认“其他 other”，要求用户确认；
4. 保存前明确显示词性，不允许无意识沿用错误默认值。

### [Bug][数据质量][P1] B-005 来源网址污染词汇表

#### 现象

来源链接被拆成 `https`、`plato`、`stanford`、`edu`、`entries` 等多个新词，进入阅读页和新词统计。

#### 精确原因

English fallback 使用正则：

`[A-Za-z]+(?:['-][A-Za-z]+)?|[0-9]+|[^\sA-Za-z0-9]`

它会把所有连续英文字母视为普通词，不在分词前识别 URL、邮箱、代码或文件路径。URL 中的域名和路径因此被分解成普通英文 token，后续流程又把这些 token 当作可学习词处理。

#### 解决方向

在 Python tokenizer 和 fallback 的共同入口增加特殊片段识别：

- URL 整体标记为不可学习 token；
- 邮箱整体标记为不可学习 token；
- 可选保留原文显示；
- 不创建 EncounteredWord，不计入新词，不进入词义候选。

### [Bug][数据质量][P1] B-006 降级分词产生过长句子

#### 现象

点击 `technicity` 后，保存的“当前句子”把标题、文章介绍和后续正文合并在一起，远长于自然句子。

#### 精确原因

fallback 只在“句号、问号或感叹号后紧跟空白”时切句：

`/((?<=[.!?])\s+)/u`

导入前，换行和段落被转换为 `ZZPARAZZ`、`ZZNEWLZZ` 等结构标记。fallback 没有把这些结构标记视为句子边界。标题本身又没有句号，于是标题与下一段被分配到同一个 `sentence_index`。

Python tokenizer 正常运行时会使用项目自定义句子切分器，并识别结构边界；服务宕机后，这部分语义没有被 fallback 完整继承。

#### 解决方向

fallback 必须在 `PARAGRAPH_BREAK`、`NEWLINE` 和 section marker 处结束当前句子，同时避免在 URL 中的句点处错误切句。

### [Bug][体验与无障碍][P1] B-007 阅读页 DOM 文本缺少真实空格

#### 现象

视觉上英文单词之间有间距，但浏览器 `textContent`、部分复制结果和无障碍树接近：

`BernardStieglerOriginalTechnicity...`

#### 精确原因

`TextBlockGroup.vue` 使用模板注释主动消除 span 之间的模板空白。普通阅读模式下，`spaceAfter` 仅转换为 CSS 类 `.space-after`，再通过 `margin-right: 4px` 制造视觉距离。CSS margin 不属于文本内容。

只有 `plainTextMode` 才在 span 内插入 `&nbsp;`。因此普通模式视觉正确，但 DOM 中没有真实空格。

#### 用户影响

- 复制文本可能粘连；
- 屏幕阅读器的朗读边界不可靠；
- 浏览器页面查找可能失败；
- 自动化和文本提取工具得到错误正文；
- 搜索、引用和辅助功能体验下降。

#### 解决方向

在不破坏逐词点击和短语高亮的前提下，让需要空格的 token 在 DOM 中包含真实空白文本节点。不能只继续增加 CSS margin。

### [Bug][后端问题][P1] B-008 Jellyfin 缺失设置导致普通导入窗口返回 500

#### 现象

打开普通文本导入窗口时，请求 `/settings/is-jellyfin-enabled` 返回 500，并显示：

`Missing jellyfinEnabled setting. This should never occur.`

#### 精确原因

`SettingValueService::isJellyfinEnabled()` 固定查询 `settings.user_id=-1`、`name=jellyfinEnabled`。查不到记录时直接抛异常。`SettingsController` 将异常转换为 500。

前端 `ImportTypeSelection.vue` 同时请求网站导入语言和 Jellyfin 状态。`axios.all` 中任一请求失败都会进入统一 catch，因此一个可选集成的缺失设置会拖累整个导入类型加载。

#### 解决方向

- 缺失时默认返回 `false`；
- 两个可选功能分别加载，不用一个请求失败拖垮另一项；
- SettingsSeeder 补齐全局默认值；
- 未配置 Jellyfin 时不向普通用户展示内部错误。

### [Bug][体验][P2] B-009 每章最大字符数的界面值可能没有提交

#### 现象

把“每章最大字符数”改为 15000 后，约 4000 字符的文章仍按默认 3000 拆成两个章节。

#### 精确原因

`ImportOptions.vue` 的数字输入只监听 `@keyup` 和 `@click`，没有监听标准的 `@input` 或 `@change`。键盘逐字输入通常会触发更新；粘贴、浏览器自动填充、自动化 fill、输入法提交等方式可能只改变控件值，不调用 `importOptionsChanged()`。父组件因此继续持有旧的默认值 3000。

#### 解决方向

以 `v-model` 的 `@input`/watcher 为唯一数据更新入口，并在最终提交时再次从表单状态读取和验证数值。

### [Bug][后端问题][P2] B-010 登录页首次字体请求返回 401

#### 现象

登录流程中第一次请求 `/fonts/get-fonts-for-language/english` 返回 401，登录完成后的同一路径返回 200。

#### 精确原因

公共登录页面已经挂载了需要读取字体配置的前端布局，但字体接口位于需要认证的路由中。前端在会话建立前即发起请求，认证中间件按设计拒绝。

#### 解决方向

登录/注册页面不应加载已登录用户字体设置；或者为公共页面提供不含用户数据的默认字体配置。

### [Bug][后端问题][P2] B-011 `reviewIntervals` 全局设置缺失

#### 现象

数据库 doctor 报告 `reviewIntervals: MISSING`。部分旧式单词 stage 更新会记录“缺失后自动写入默认值”。

#### 精确原因

当前项目同时存在旧的 EncounteredWord stage 间隔设置和新的 FSRS preset 设置体系。初始化数据库没有写入旧路径仍会读取的 `reviewIntervals` 全局记录，导致运行时补种和诊断结果不一致。

#### 解决方向

先确认 `reviewIntervals` 是否仍是必要兼容设置：

- 仍需要：由 Seeder 一次性写入，不在业务请求中临时补种；
- 已废弃：移除运行时依赖和 doctor 检查，避免两套设置并存。

### [Bug][监督工具链][P0] B-012 Reasonix 监督发送、排队与直接引导链路仍不可靠

详细子台账：

`docs/plans/reasonix-supervision-toolchain-bug-ledger-2026-08-05.md`

## 五、待优化台账

### [待优化][权限设计] O-001 注册页面增加“管理员账号”选项

#### 当前实现

`LoginForm.vue::registerUser()` 固定调用：

`createUser(this.register, false, ...)`

因此注册页没有管理员选项，并始终向后端发送 `isAdmin=false`。

后端 `UserController::createUser()` 还有第二层保护：匿名公共注册只要不是第一个用户，就会强制把 `$isAdmin` 改为 `false`。这能防止任何访客勾选管理员后自行提权。

#### 产品要求

注册账号页面增加“创建为管理员”选项。

#### 安全边界

不能简单把公开注册页的复选框直接传给后端，否则会形成管理员提权漏洞。可接受方案：

1. 第一个账号仍自动成为管理员；
2. 后续匿名注册只能创建普通账号；
3. 只有已登录管理员进入受保护的账号创建入口时，才显示并允许“管理员账号”；
4. 后端必须再次验证当前操作者是管理员，不能信任前端布尔值；
5. 保证系统始终至少有一个管理员。

当前 `/register` 在已登录状态会重定向回首页，因此若坚持复用“注册页面”的视觉形式，需要新增一个受管理员保护的创建模式，不能直接开放匿名管理员注册。

### [待优化][前后端] O-002 点击词语时存在重复请求

#### 现象

一次词语点击会请求 AI 上下文、词义候选、已学词义、阅读内预览和词典。实测同一个 `/chapters/ai-assist/lookup/{chapterId}` 在一次交互中出现重复请求。

#### 精确原因

桌面侧栏和弹出式词汇框各自包含 AI 建议加载逻辑。相关组件在 mounted、词元变化和上下文变化时都会调用 `loadAiSuggestions()`，缺少统一请求层、请求键缓存、在途请求复用和旧请求取消。

#### 解决方向

按 `chapter_id + sentence_index + surface + lemma` 建立共享查询键：

- 同一键的并发调用复用同一个 Promise；
- 短时间内缓存结果；
- 选择切换时取消旧请求；
- 侧栏与弹窗消费同一份 store 数据。

### [待优化][后端噪声] O-003 WebSocket/Pusher 在未启动服务时持续报错

#### 现象

页面反复尝试连接 `ws://127.0.0.1:6001` 和 `wss://127.0.0.1`，控制台持续出现连接拒绝。

#### 精确原因

`resources/js/vuex/Shared.js` 在前端初始化时直接创建 Laravel Echo/Pusher 客户端。当前本地没有对应 WebSocket 服务，也没有先通过配置或健康检查决定是否启用实时广播，因此每次页面加载都会发起失败连接。

#### 解决方向

- 增加 `realtimeEnabled` 配置；
- 默认本地关闭，或统一启动 WebSocket 服务；
- 关闭时使用已有 emptyEcho，不发起网络连接；
- 不用失败重连充当功能探测。

### [待优化][后端风险] O-004 ECDICT 导入缺少原子替换

#### 当前行为

导入命令会删除正式词典表、重新建表，然后按批次提交数据。

#### 风险原因

如果导入中途断电、数据库异常或进程退出，正式表可能只包含部分词条。虽然健康检查能发现数量不足，但故障发生后用户已经处于不完整词典状态。

#### 解决方向

导入到临时表，完成数量、字段和抽样检查后，再在一个短事务内切换正式表和 metadata。

### [待优化][诊断] O-005 Database Doctor 固定检查 user 1

#### 现象

当前主账号内部 id 并非 1，但 doctor 输出仍显示“Goals (user 1, english)”。

#### 精确原因

诊断命令的目标用户被固定为 1，没有根据实际账号、邮箱或命令参数解析用户。

#### 解决方向

增加：

- `--user-id=`；
- `--email=`；
- 未指定时检查第一个现存管理员；
- 输出被检查账号的邮箱和 ID。

### [待优化][可维护性] O-006 可选功能缺失不应统一抛 500

#### 原因

Jellyfin、Anki 和部分全局设置读取采用“记录不存在即抛异常”的策略。可选功能未配置属于正常状态，不属于服务器内部故障。

#### 解决方向

为每个设置明确三种语义：

- 必需设置缺失：启动诊断失败；
- 可选设置缺失：返回安全默认值；
- 用户设置缺失：按用户默认值初始化。

避免在页面访问期间临时补种或用 500 表示“尚未配置”。

### [治理][当前规则] G-001 当前开发执行方式

当前有效方式已经由用户确认：

1. 本地 Codex 直接处理；或
2. 网页端 GPT 通过 DevSpace 直接处理；
3. 两种方式在文件发现、搜索、读取、替换和命令执行中都优先使用 FastCtx。

以下流程均已停用：

- “一个主执行 Agent 对全部结果负责”；
- OpenCode → CodeBuddy → WorkBuddy 接力；
- CodeBuddy / WorkBuddy 固定复核链。

#### 精确原因

项目工具链已转向网页端直连本地工作区和本地 Codex 执行。旧角色接力会重复传递上下文、增加报告噪声，也不能反映当前可调用工具。部分规则文档和测试仍锁定旧流程，因此当前问题是文档/Harness 漂移，不是产品代码缺陷。

#### 后续动作

独立执行“规则正文 + guard + 历史标记”同步迁移，不能只删文档或只删失败测试。

### [未来计划][协作架构] F-002 网页端 GPT 与 Codex++ 并行分工

#### 目标

网页端 GPT 制定一份总计划，把互不冲突的任务分别分给：

- 网页端 GPT 通过 DevSpace 执行；
- 本地 Codex++ 执行；
- Codex++ 接入 DeepSeek Flash，并可进一步指挥接入相同 API 的扩展并行工作。

#### 当前状态

规划中，尚未完整实现。不得在报告中写成已经具备的能力。

#### 必须先解决的原因与风险

- 两方可能同时修改同一文件，产生覆盖；
- 两方可能同时写测试数据库，造成假失败或数据污染；
- DeepSeek Flash 执行速度快，但缺少足够细的计划时容易扩大范围；
- 最终结果可能分别通过局部测试，却在合并后冲突；
- 网页端和本地上下文可能读取到不同 Git 状态。

#### 启用门槛

- 单一任务账本和任务 owner；
- 每个任务明确文件白名单；
- 同一文件和共享数据库写入禁止并行；
- 只读侦查、独立文档、互不重叠测试可以并行；
- 全过程 FastCtx；
- 汇总方重新检查最终 diff、测试和真实页面；
- 失败方不得自动扩大范围替另一方补做。

### [架构][P0] A-001 启动、Readiness 与默认数据没有统一所有者

#### 覆盖问题

- Python tokenizer 未运行；
- 新账号 goals 与 statistics 竞态；
- Jellyfin、Anki、`reviewIntervals` 缺失；
- WebSocket 未启用仍连接；
- 登录前字体接口 401。

#### 精确原因

项目把“必需运行服务”“可选能力”“用户默认数据”混在页面访问、Seeder、运行时补种和独立脚本中。前端页面因此承担了能力探测，后端又假设部分记录必然存在。

#### 目标架构

统一 Readiness/Capability 层：必需服务启动失败应阻断或强警告；可选能力缺失返回 disabled；用户默认数据在账号创建事务中建立，并保留幂等修复入口。

### [架构][P1] A-002 导入流水线缺少统一 Preflight 和原子提交

#### 覆盖问题

- URL 污染词汇；
- fallback 长句；
- tokenizer 不可用后直接降级；
- ECDICT 边删边导；
- 每章字符数界面值与提交值不一致。

#### 精确原因

来源获取、内容分类、分词服务检查、结构边界恢复、预览验证和持久化由不同入口独立处理，没有一个统一的导入事务边界。

#### 目标架构

来源获取 → 特殊片段分类 → tokenizer readiness → 结构化分词 → 用户预览 → 临时表/临时实体 → 验证 → 原子切换 → 导入后健康证据。

### [架构][P1] A-003 语义文本与视觉渲染混用

#### 覆盖问题

阅读页依靠 CSS margin 显示空格，但 DOM 没有真实空白。

#### 精确原因

token 展示模型只保存“视觉上是否留白”，没有同时维护“复制、搜索、朗读所需的语义分隔”。

#### 目标架构

Token Presentation Policy 同时输出可点击 token 节点和真实文本分隔；视觉样式不能替代 DOM 语义。

### [架构][P1] A-004 Reader 查询副作用存在多个所有者

#### 覆盖问题

同一次点词可能重复请求 AI 上下文、词典和已学词义。

#### 精确原因

桌面侧栏、弹出词汇框和其他展示组件各自在 mounted/watch 中加载数据，缺少共享 request key、在途 Promise 复用、缓存和取消机制。

#### 目标架构

以 `chapter_id + sentence_index + surface + lemma` 为查询键，建立单一 Reader Lookup coordinator；UI 组件只消费状态。

### [架构][P1] A-005 可选集成没有 Capability 边界

#### 覆盖问题

Jellyfin、Anki 和 WebSocket 通过失败请求探测是否可用。

#### 精确原因

“功能未配置”被表示成 500 或连接拒绝，而不是明确的 disabled 状态。

#### 目标架构

启动时形成只读 capability snapshot；未启用时不创建客户端、不请求、不重连；配置错误只向管理员显示诊断。

### [架构][P1] A-006 用户生命周期缺少完整领域入口

#### 覆盖问题

测试用户积累、doctor 固定 user 1、管理员创建和完整用户删除不统一。

#### 精确原因

项目有创建、编辑和按语言删数据，但没有完整的 User Lifecycle service 负责默认数据、管理员不变量、删除依赖和测试账号清理。

#### 目标架构

管理员创建模式与匿名注册分开；后端验证权限；禁止删除最后一个管理员和主账号；事务清理全部用户数据；doctor 接受 email/user-id。

### [架构][待优化] A-007 Service 数量增长且目录仍较平

#### 事实

官方原项目有 20 个 Service，当前有 142 个；其中约 50 个不超过 100 行，18 个不超过 50 行。除 CustomStudy 和 Settings 外，大量 Service 平铺在 `app/Services`。

#### 原因

多轮安全抽取成功建立了单一 owner，但抽取单位主要按任务推进，没有同步建立稳定领域包和统一入口。一部分薄 Service 可能只是转移代码。

#### 风险

查找一个功能需要在大量相近命名文件间跳转；新 Agent 容易重复创建 Service；跨领域调用关系不直观。

#### 优化原则

不按行数合并。先画依赖和调用图；保留有独立不变量或副作用 owner 的 Service；没有独立契约、只有单一转发且不降低复杂度的薄层才进入合并候选。

### [架构][待优化] A-008 路由和公开入口接近翻倍

#### 事实

`routes/web.php` 的 Route 声明从官方原项目约 116 增至约 223。

#### 原因

新增 sense-only、FSRS、Browser、Custom Study、Preset、AI Study Card、统计和诊断功能，但仍集中在大型 `web.php`。

#### 风险

路由顺序、动态参数吞掉固定路径、鉴权组遗漏和重复 endpoint 更难审查。

#### 优化方向

按领域拆 route 文件或 route registrar；保持中间件和命名一致；禁止只为减少 `web.php` 行数机械拆分。

### [架构][待优化] A-009 Legacy 与新主线并存形成兼容负担

#### 事实

legacy word review、EncounteredWord stage、旧 settings 与 sense-only FSRS 主线并存。

#### 原因

当前项目在不破坏原有功能的前提下逐步增加 sense-only 架构，因此保留兼容入口和数据。

#### 风险

两套设置、队列和页面可能继续漂移；开发者可能误把 legacy 当新功能入口。

#### 处理原则

在产品未决定移除前保留测试和明确标记；未来按独立阶段统计真实使用、冻结迁移方案，再成套删除代码、路由、设置和测试。

### [测试治理][P1] T-001 测试规模已成为独立维护成本

#### 事实

当前约 264 个测试文件、93,128 行，约为生产与工具代码的 91%。官方原项目只有约 214 行测试。

#### 原因

当前增加了 FSRS、权限、删除、来源、Preset、Custom Study 和 AI 边界，同时多轮任务不断追加回归、源码 guard 和文档 guard，较少进行合并审计。

#### 结论

测试多不是删除理由。应建立测试资产清单：保护的不变量、对应生产 owner、最后一次捕获回归、是否有更稳定替代证据。

### [测试治理][待清理] T-002 精确行数、日期和阶段文案 guard 过度脆弱

#### 现象

测试锁定 Vue 精确行数、文档日期标题、阶段 `not started` 和旧 Agent 名称。

#### 精确原因

一次性的阶段验收事实被误当成长久架构不变量。

#### 处理

改为验证职责 owner、危险调用不存在、接口和状态语义；语义替代测试建立后删除旧断言。

### [测试治理][待清理] T-003 源码字符串 UI guard 与行为测试可能重复

#### 事实

启发式扫描约有 87 个、16,262 行测试具有源码或文档 guard 特征，占测试约 17.5%。该数字只是审计池，不等于可删除量。

#### 精确原因

早期缺少稳定组件测试工具，使用 PHP/Node 读取 Vue 源码来锁定文案和方法名；后续真实浏览器和 contract tests 增加后，部分旧 guard 没有退出。

#### 删除条件

同一行为必须已经由组件行为测试、后端 contract 或真实 browser smoke 覆盖；删除后仍保留正常、拒绝和副作用证据。

### [测试治理][待优化] T-004 超大型测试文件和重复 Fixture

#### 事实

`ReviewCardManageTest.php` 约 4,538 行，`WordSenseTest.php` 约 3,193 行，多个 Feature test 超过 1,500 行。

#### 原因

功能每扩展一次就在同一文件追加用例；用户、语言、卡片和来源 fixture 反复手工创建。

#### 优化方向

按业务契约拆文件；共享受控 fixture builder；用数据驱动合并重复排列。目标是降低重复准备代码，不能减少风险场景。

### [测试治理][保留] T-005 Legacy 测试只能随 Legacy 功能成套退出

当前 legacy word review 和兼容设置仍存在。不能先删测试来降低数量，否则会把兼容层变成无保护代码。只有产品批准移除、迁移和真实数据验证完成后，才能同时删除入口、实现和测试。

### [文档治理][待清理] D-001 当前文档仍携带大量历史执行报告

#### 事实

master plan、handoff、FSRS roadmap 和 hotspot audit 合计超过四千行，同一完成状态、测试数字和 Agent 报告重复出现。

#### 原因

过去每轮把报告追加回当前文档，却没有把关闭阶段移动到 history。

#### 处理

`CURRENT_AI_CONTEXT.md` 保留当前事实；索引只路由；历史报告迁入 history；ADR 保留稳定决定；guard 不再锁定会变化的数字。

### [本地环境][待清理] L-001 `.playwright-cli` 与根目录验收产物大量堆积

#### 事实

当前工作树存在大量未跟踪的页面快照、console log、临时 PHP/JS、图片和结果 JSON。

#### 原因

真实浏览器验收每轮生成新文件，但缺少统一临时目录、忽略规则和完成后清理流程。

#### 风险

工作区状态难读，Agent 容易误提交生成物，也会干扰文件搜索。

#### 处理边界

本轮只登记，不自动删除 `.playwright-cli` 或未知临时文件。后续先区分仍需作为证据的文件与纯临时产物，再增加统一 ignored artifact 目录和清理命令。

- 测试增加约 92,914 行；
- 文档增加约 37,610 行。

两个仓库没有共同 Git 祖先，因此这是快照差值，不是提交历史意义上的精确新增行数。

### [架构评估][结论] C-002 双方屎山程度

- 官方原项目生产代码约 `6.7/10`：体量小但大组件、宽 Service、隐藏状态和几乎无测试，耦合型屎山更高。
- 当前生产代码约 `5.7/10`：领域 owner、权限、事务和测试更合理，但 Reader/Reviewer/import 仍有热点。
- 当前整个仓库维护负担约 `6.4/10`：测试、文档、guard、legacy 和临时产物形成新的治理泥沙。

结论：当前架构更合理、更安全；原项目更容易快速看懂；原项目代码耦合更重；当前仓库治理负担更重。

## 八、Anki 功能与架构对比新增台账

完整通俗对比见：

`docs/architecture/anki-function-and-architecture-sales-comparison-2026-07-23.md`

本轮信息来源分为三层：Anki 官方手册确认产品行为，Anki 官方仓库确认真实模块与接口，Anki Forums 只用于发现用户痛点和趋势。论坛意见不得自动升级为产品决定。

### [产品已接受][P0] ANKI-001 自动备份与用户可操作恢复

#### 现象

项目存在备份相关代码，但还没有形成像成熟学习软件那样清楚的自动备份、备份列表、恢复预览、恢复确认和误覆盖防护体验。

#### 架构原因

备份目前更接近工具能力，没有成为用户生命周期和数据安全架构中的一级领域。恢复操作涉及用户数据、媒体、学习进度和当前数据库状态，却没有统一 restore plan、差异预览和可撤销边界。

#### 处理方向

先建立本地自动备份与时间点恢复，再评估跨设备同步。恢复前必须显示将覆盖的数据范围，并保留恢复前安全快照。

### [产品差距][P1] ANKI-002 缺少成熟的跨设备同步与冲突处理

#### 现象

当前主要通过本地网页系统使用，没有成熟的离线客户端、媒体同步、增量变更合并和双向冲突处理。

#### 架构原因

现有 Web 多用户数据库默认只有一个服务器事实源，没有离线 change journal、稳定对象版本、设备游标和冲突合并协议。

#### 处理方向

不要直接复制完整 Anki 同步。先保证单服务器账号数据、备份和导出可靠；真正双向离线同步作为单独长期项目。

### [产品已接受][P1] ANKI-003 WordSense Tag

#### 现象

已有 ReviewCard Marker，可标记单张卡；但不能像 Anki Note Tag 一样给一个词义同时添加“技术哲学”“论文高频”“易混淆”等多个内容标签。

#### 架构原因

Card Marker 已明确属于 ReviewCard，WordSense Tag 属于内容对象。两者如果混用，会让卡片关注状态和知识分类互相污染。

#### 处理方向

新增独立 WordSense Tag 领域，支持层级标签、批量编辑、搜索和 Custom Study；禁止把 Marker 直接改造成多标签字段。

### [产品已接受][P1] ANKI-004 统一搜索条件

#### 现象

Browser、Saved Search、Custom Study、导出和统计都有筛选能力，但同一条件不能稳定跨区域复用。

#### 架构原因

各页面在不同阶段分别增加 filters、Criteria 和 query 参数，缺少共享 Search AST、字段词典和错误契约。

#### 处理方向

先收敛现有条件为统一 Criteria；同一 Saved Search 可用于 Browser、Custom Study、导出和统计。无需一次照抄 Anki 全部搜索语法。

### [产品已接受][P1] ANKI-005 更完整的统计

#### 现象

当前已有今日总结、七日趋势、三十日视图和部分学习反馈，但缺少统一的未来到期负担、真实保持率、retrievability 分布、来源贡献和阅读转化统计。

#### 架构原因

统计能力按页面和阶段增长，尚未形成共享指标定义、查询范围和时间窗口层。

#### 处理方向

优先补未来 7/30/90 天负担、True Retention 类指标、最常失败词义、文章来源贡献和阅读转制卡率。每项指标必须有统一定义，不能在前端临时计算。

### [产品已接受][Planning Required] ANKI-006 `.apkg` 内容卡导出 V1

#### 已确认卡片内容

一个 WordSense 导出为一张固定模板卡：

```text
单词：...
释义：挖空 1

1. 原文：该释义对应的真实例句 1
   翻译：挖空 1
2. 原文：该释义对应的真实例句 2
   翻译：挖空 1
3. ……
```

#### 已确认边界

- 例句列出该释义对应的全部真实来源例句，并使用有序列表。
- 释义挖空；每条例句的中文翻译也挖空。
- 首版只做 `.apkg` 内容卡导出，不宣称完整双向同步。
- 当前不包含图片、音频或其他多媒体。

#### 仍需 Spec 冻结

- 单词显示 surface、lemma，还是两者同时显示；
- 没有中文翻译时的卡面；
- 例句过多时是否设上限；
- 是否导出当前 FSRS 调度；
- 重复导出时更新、跳过还是新建。

### [产品已接受][文章范围] ANKI-007 文章健康检查

当前只检查文章、章节、分词结果和原文来源，不考虑图片、音频或其他多媒体。

优先检查：

- 空文章、重复章节、章节顺序和段落结构；
- tokenizer 是否降级；
- URL、邮箱、路径是否污染词汇；
- WordSenseOccurrence 是否指向存在的文章和句子；
- 原文定位是否大量 fallback；
- 孤立来源和损坏导入记录；
- 修复前预览、备份和失败回滚。

### [产品已接受][语义待讨论] ANKI-008 Custom Study 向 Anki 靠拢

产品方向已接受：Custom Study 仍是单独卡片复习入口，兼容的 Anki Filtered Deck / Custom Study 能力尽量学习。

当前实现仍为 preview-only。以下问题没有冻结，因此暂时保留现有 Harness：

- 临时会话是否正式评分；
- 提前复习、增加今日卡片、处理积压和任意搜索临时学习是否使用同一语义；
- 评分如何影响正常队列；
- 会话结束后如何回归；
- 同一卡当天进入多个临时会话如何计数。

本项是产品方向接受，不是代码实现授权。

### [产品已接受][兼容项优先] ANKI-009 更多复习设置

#### 现象

已覆盖 desired retention、FSRS 参数、每日上限和队列顺序；尚未覆盖学习/重学步骤、Easy Days、自动前进、计时器、完整音频和兄弟卡埋藏等。

#### 判断

产品方向已接受：Anki 已有、且与 sense-only FSRS 兼容的设置逐项学习；完全依赖 sibling cards、任意 deck 树或通用 Note Type 的设置放弃。每项设置必须说明默认值、用户影响、是否追溯旧卡和是否需要显式重排。

### [明确不进入] ANKI-010 通用 Note Type / Card Template 编辑器

#### 原因

Anki 允许任意字段、HTML/CSS 模板和一条 Note 生成多张 Card。LinguaCafe 依赖固定 WordSense 结构来保证词义、来源、lemma、AI 确认和 FSRS 身份。

#### 风险

引入通用模板会使字段语义不再稳定，显著增加来源绑定、删除、归档、兄弟卡、AI 和 Browser 复杂度。

#### 决定

除非产品转型为通用制卡平台，否则不进入近期计划。

### [明确不进入] ANKI-011 任意 Deck/Subdeck 树

#### 原因

LinguaCafe 已有用户、语言、文章来源、WordSense Tag 候选和 Saved Search。任意牌组树会增加另一套重叠分类和 Preset 归属冲突。

#### 替代方向

语言边界 + WordSense Tag + Saved Search + 临时学习会话。

### [产品已接受][长期架构] ANKI-012 受控插件接口

插件接口是长期重要能力。首批优先支持导入器、词典、AI Provider、导出器和只读分析插件。

必须采用版本化接口、权限声明、默认最小权限、可停用、错误隔离和兼容版本提示。插件不得绕过正式评分、ReviewLog、用户权限、删除确认或密钥保护。安装来源、签名、审核、沙箱、移动端支持和收费模式继续讨论。

### [明确不进入当前计划] ANKI-013 Cloze 与 Image Occlusion

当前外语阅读和哲学文本主线不建设通用 Cloze 或 Image Occlusion。未来只有产品方向扩展到图表、医学或视觉学习时才重新提出，不保留隐含开发承诺。

### [产品已接受][P1] ANKI-014 Browser V2 与 AI 重复词义整理

Browser 可继续增加 WordSense Tag 批量管理、更多列、统一搜索、Saved Search → Custom Study 和重复词义检测。

重复词义整理使用文件闭环：LinguaCafe 打包词义库和固定提示词，用户交给外部 AI，AI 返回固定格式的“重复 / 近义但缺区分 / 可能合并 / 应保留”结果；LinguaCafe 只解析和显示差异。AI 不得直接删除、合并或改写 WordSense，正式变化必须人工确认，并具备备份和撤销方案。

### [架构][待优化] A-010 缺少类似 Anki Proto 的稳定契约层

#### 现象

Anki 使用 Protobuf 定义前后端接口并生成 Rust、Python、TypeScript 绑定。LinguaCafe 大量接口仍由 Laravel route、数组 payload 和前端 axios 共同约定。

#### 风险

字段漂移常依赖字符串 guard 发现；前端可能直接拼 URL、重复解析错误和复制响应结构。

#### 优化方向

不必照搬 Protobuf。可先建立 Request/Response DTO、统一错误码、领域 API client、TypeScript 类型和 payload contract tests。

### [架构][待优化] A-011 Search、Custom Study 与统计查询模型分散

#### 原因

不同阶段分别实现筛选、Saved Search 和 Criteria，没有统一字段注册表、AST 和权限应用器。

#### 优化方向

形成共享 Criteria/Search 领域；权限与 user/language 隔离只在一个查询入口应用。

### [架构][待优化] A-012 撤销能力缺少统一 Operation 目录

#### 现象

已有评分撤销、FSRS 重排撤销、阅读确认撤销等多个实现，但用户不知道哪些动作能撤销、有效多久、恢复了什么。

#### 优化方向

先建立 operation registry 和统一响应格式，不一次重写全部撤销实现。

### [架构][不可避免] A-013 Reader/Tokenizer 复杂度不能按 Anki 模型删除

Anki 通常从用户已填写的卡片开始；LinguaCafe 必须从连续文本识别词、lemma、句子、段落和来源。Tokenizer、fallback、结构恢复和 readiness 是产品特色带来的必要成本，只能明确边界，不能为了代码更少而移除。

### [架构][不可避免] A-014 WordSense 与来源证据增加数据层复杂度

一个具体词义必须关联阅读位置、例句和多个 occurrence。这比 Anki 把字段作为普通文本复杂，但正是“阅读产生学习材料”的核心价值。

### [架构][产品讨论] A-015 本地 Profile 与登录权限边界重新开放

Anki 桌面端支持无密码 Profile 选择，每个 Profile 有独立 collection 和设置；但 AnkiDroid 不支持桌面式多 Profile，需要同步的 Profile 还必须使用独立 AnkiWeb 账号。

用户希望 LinguaCafe 复刻本地 Profile 选择并取消密码。该方向尚未冻结：必须先决定本机、远程访问、手机端、云同步、付费账号和管理员操作的安全边界。在讨论完成前，现有 user/language 数据隔离继续保留，不删除密码和权限代码。

### [架构][产品已冻结 / 待 Architecture Gate] A-016 阅读中直接刷词义卡 V1

该方向已于 2026-07-24 在 PD-012 完成产品语义冻结：先形成浏览器内待确认评分，确认具体 WordSense 后才通过正式 Sense Review 路径写入 ReviewLog 与 FSRS；取消或切换目标词时清空待确认评分，同一 ReviewCard 需要重复抑制，正式写入后的 Ctrl+Z 复用现有快照撤销。

当前只允许进入 Architecture Spec、ADR 与 Harness 迁移设计，尚未获得业务代码实现授权。现有“阅读确认不等于正式评分”的代码和 Harness 在架构迁移方案获批前继续保留，不能提前删除或直接改造成评分接口。权威正文见 `docs/product/confirmed-product-decisions-and-discussion-roadmap-2026-07-23.md` 的 PD-012。

### [治理][信息来源] G-002 Anki 论坛只作为需求雷达

2025–2026 年论坛持续出现同步、FSRS 模拟、Browser、插件、Image Occlusion、移动端和无障碍讨论。这说明成熟功能仍有长期边界问题。

使用规则：

1. 官方手册定义当前产品语义；
2. 官方仓库确认真实架构和接口；
3. 论坛用于发现用户困惑和需求；
4. 论坛单一帖子不得直接冻结 LinguaCafe 产品方案。

### [待讨论] DISC-001 新文章 AI 生词建议与批准步骤

系统先标出生词、打包给 AI、粘贴 AI 返回结果，再进入默认开启且可关闭的批准步骤。首次提示只在确认窗口中用一行文字说明关闭路径。生词标准、批准对象、默认选择、提示次数和与现有 AI Study Card V1–V5 的合并方式尚未冻结。

### [待讨论] DISC-002 翻译显示与文章排版

当前显示/关闭翻译导致正文伸缩和阅读位置跳动，已确认属于体验问题。候选为“一句话一行 + 段落编号 + 段末分隔线”，或“连续正文但预留翻译空间”。默认方案、长句、窄屏和缺翻译留白尚未冻结。

### [待讨论] DISC-003 手机端、三平台与商业模式

未来目标包含 Android 和 iPhone。Web/PWA、跨平台壳或原生应用，离线能力、插件兼容、同步身份、免费/收费边界、AI 成本和是否保留桌面端尚未冻结。

详细决定和四轮讨论路线见 `docs/product/confirmed-product-decisions-and-discussion-roadmap-2026-07-23.md`。
