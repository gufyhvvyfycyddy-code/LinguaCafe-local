# ADR-0037：目标模式非阻断执行前沿

> 状态：Accepted under current user authorization
> 日期：2026-07-28
> 决策者：用户
> 适用范围：当前及以后明确指向权威 roadmap 或有序里程碑的持续目标

本 ADR 部分取代 ADR-0001、ADR-0031 和 ADR-0034 中会把切片文档、脏工作区、
独立 deferred 分支或单一外部步骤升级为全局人工闸门的语义。生产/真实用户
数据、秘密、外发、付费、部署、签名、发布和破坏性操作停止线不变。

## 1. 背景与本次授权

用户已经连续明确要求：

- 完成全部命名里程碑，必要时修改规则；
- Anki 有适用官方设计时采用其设计，否则使用 Agent 推荐的最小方案；
- 不因可自行处理的选择、工具失败或流程规则反复请求确认；
- 本次再次授权检查并修改仍会造成阻断的规则，并允许使用全部可用工具。

对抗审查表明，ADR-0034 已处理大部分重复停顿，但仍有四个可预见的全局阻断：

1. 工作区已有修改可能被机械解释为“文件不可编辑”；
2. 当前目标内的切片 plan/ADR 可能再次等待网页端或用户逐份 Accept；
3. 全局只允许一个 deferred 前置会冻结语义独立的其他依赖分支；
4. 一个必须人工或外部完成的动作可能过早冻结全部本地可执行工作。

## 2. 唯一的阻断分类

执行 Agent 遇到问题时必须先分类，不得把所有失败都称为“受阻”：

1. **可解决的执行问题**：缺文件、测试失败、普通工具/进程/端口/会话故障、
   当前切片内遗漏文件或可逆实现选择。诊断、修复、更新 allowlist 或切换
   平台允许的通道后继续，不请求用户。
2. **可延期证据**：实现和自动验证已通过，但浏览器、原生设备或外部环境证据
   当前无法取得。按 ADR-0034 记录
   `Acceptance Deferred — Not Complete`，只暂停依赖该缺失行为的分支。
3. **保留停止线**：需要新的产品边界、真实/开发/生产数据破坏性操作、秘密、
   外发、付费、部署、签名、发布，或同一最高权威内不可消解冲突。只暂停受
   影响切片；若依赖图还有其他已授权切片，先继续其他切片。
4. **全局阻断**：所有尚未完成切片都传递依赖同一个第 2/3 类事项，或最终完成
   审计只剩必须由用户/外部环境完成的事项。只有此时才向用户请求具体动作。

报告必须使用上述分类并指出受影响依赖边；“一个动作不能做”不等于“目标受阻”。

## 3. 切片文档的接受语义

当前目标及用户在 ADR-0031、ADR-0034 和本 ADR 记录的确认，已经接受：

- 权威 roadmap 中的命名里程碑和依赖顺序；
- 决策梯第 4、5 步产生的、目标内、可逆、兼容且可测试的推荐；
- 为落实这些已接受决定而生成的切片 Architecture Gate、plan、contract 和 ADR。

因此，执行 Agent 可以把这类文档标记为
`Accepted under current goal authorization` 或 `Frozen for implementation`，
并直接实施；这表示对用户既有决定的忠实展开，不是 Agent 自行批准新的产品
边界。只有文档新增 ADR-0034 §3 保留决定时，才需要新的用户决定。

Architecture Gate 仍必须在编码前冻结责任、非目标、文件、seam、数据流、
兼容边界和验证，但它是可执行安全检查，不是每个切片的人工作流暂停点。
缺少某个可选 persona、HTML 报告或单一审查工具时，可用 FastCtx 代码侦察、
等价的独立对抗审查和可执行负向测试满足相同证据，不得因工具名称不可用停工。

## 4. 脏工作区的语义合并

已有工作区改动始终是用户资产，但“有改动”本身不构成阻断。修改重叠文件前：

1. 读取目标文件和其当前 diff；
2. 用最小补丁保留既有语义和无关改动；
3. 只验证、报告并在提交时暂存本切片的精确变更；
4. 不 reset、checkout、覆盖、清理或顺带提交用户改动。

若同一代码行或同一契约的未提交用户改动与当前切片要求实质互斥且无法同时
保留，必须保持用户改动原样并只暂停受影响文件/切片。仍有独立授权切片时先
继续；只有没有任何可运行切片或最终审计需要该冲突文件时才请求具体决定。
未提交用户资产不进入文档权威层级，也不得被“低权威自动消解”。大量未跟踪
文件、无关测试残渣或其他模块修改不得自行升级为全局阻断。

## 5. Deferred capability 前沿

ADR-0052 取代旧的数字化 deferred 路径预算：

- 缺失证据按 Android 设备、iOS 签名设备、商店提交、真实 provider 等具体
  capability cluster 跟踪，每个未观察行为都是命名的
  `Acceptance Deferred — Not Complete` 检查；
- 新切片不得直接或间接依赖缺失的页面、原生或外部行为，但可继续消费已执行
  验证的稳定契约；
- 同一路径或同一能力簇可以登记多个缺失检查，不因数量自动把后续实现标成
  blocked，也不得用改名、handoff、签名待办、发布待办或 provider 待办逃避登记；
- 只有实现本身必须消费未验证行为、触及保留停止线或同一最高权威仍冲突时，
  才暂停实际受影响切片；
- Architecture Gate 必须列出实际依赖边和独立性证据，不能只声明“看起来独立”；
- 最终目标完成审计必须清零所有 capability clusters 和其中每个命名检查。

这允许继续完成独立本地工作，同时禁止把未验收行为当成下游前提或完成证据。

## 6. 人工与外部动作的调度

验证码、双重验证、系统级确认、真实 provider、签名、商店提交和部署等未获
具体授权或当前环境无法完成、但又是里程碑完成必需的动作，按 §5 标记为
`Acceptance Deferred — Not Complete` 并归入对应 capability cluster。执行
Agent 应：

1. 保存可复验 handoff、模拟、测试和缺失证据；
2. 在依赖图中标记该节点，不把 handoff 冒充完成；
3. 自动选择另一个不依赖该行为的已授权切片；
4. 仅当没有任何可运行切片或最终审计需要清零该节点时请求用户。

平台明确禁止同一结果的 alternate surface/workaround 时，不得换工具规避；
该动作进入第 2 或第 3 类，但目标的独立执行前沿继续推进。

任何验收写入前必须取得绑定同一监听 host/port 和进程的 server-bound 可执行
证据，确认实际接收浏览器请求的 HTTP 进程为 `APP_ENV=testing`、数据库连接
指向专用 testing 数据库，并能读取 testing-only sentinel。单独 PHPUnit 或
CLI testing DB 健康检查只是前置条件，不证明当前服务器。证据可来自
testing-only 本地健康端点，或绑定 PID/端口的启动证明加同源 sentinel 请求；
不得暴露连接信息或凭据。普通开发服务器、无法证明数据库目标的进程或普通
开发数据库只允许只读诊断；不得执行评分、Tag、Marker、导入、fixture 或其他
验收写入。

## 7. 完成语义与安全边界

目标模式可以“持续推进”但不能“虚假完成”：

- 自动测试、浏览器、原生、外部和人工必需证据按各里程碑契约逐项记录；
- deferred/blocked/open 节点不是 Accepted、Closed 或 Completed；
- `complete` 只在全部必需里程碑和证据真实关闭，且 deferred/blocked 节点
  全部清零后设置；
- 真实用户或普通开发数据库上的 migration、回填、恢复、删除，任何清库命令，
  秘密、真实 provider、外发、付费、部署、签名和发布仍需具体授权；
- system、developer、工具和连接器安全策略始终高于本 ADR。
